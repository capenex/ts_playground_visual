# 性能诊断报告

- 日期：2026-10-21
- 基线：`main` / `e73f9fd`（feat: improve arrow function parsing and editor UX）
- 范围：TypeScript / Python 执行与调试、CodeMirror 输入、可视化渲染、静态资源加载
- 状态：只做诊断与实测，未修改项目源码

## 摘要

日常规模（约 20–40 行）的代码输入、步进和渲染是流畅的。真正的问题集中在三类：

| 优先级 | 问题 | 主要触发条件 | 影响 |
|---|---|---|---|
| P1 | `stripTypes` 的 `<` 扫描为 O(n²) | 大文件中出现 `<` 比较，且后面没有 `>` | 键盘输入卡顿，可达数百毫秒 |
| P1 | TS 调试每步都从头重放 | 长轨迹执行“运行到下一个检查点/结束” | 主线程同步冻结 2–5 秒以上 |
| P1/P2 | Python 大结构快照过重 | 二维 DP、深递归、大容器 | Worker 执行与主线程构建都明显变慢 |
| P3 | 每步全量重渲染、资源无缓存 | 长轨迹、部署后重复刷新 | 步进延迟升高，首屏/刷新成本增加 |

现有 `test-pipeline.mjs` 在当前基线全部通过。本报告中的绝对毫秒数用于比较量级和趋势，不是跨机器的性能承诺。

## 测试环境与方法

- Windows 10.0.26200 / x64，Node.js 24.18.0。
- 本地静态服务：`node python/serve.mjs`，仅监听 `127.0.0.1`，诊断端口 `5187`。
- 浏览器：Qoder 内置 Chromium 页面，未做 CPU 降频。
- Pyodide：浏览器已有缓存，初始加载约 1 秒；未测冷缓存/CDN 首载。
- 计时：页面内 `performance.now()`，同步调用应用现有函数。
- 代码样本：项目内置样例加合成文件；合成文件用于放大问题，不是实际用户代码。
- 重复项优先取 3 次中位数；大场景为单次测量。
- 未覆盖：手机/低性能设备、真实公网、长时间内存泄漏、视频导出逐帧性能、生产环境缓存。

## 详细发现

### P1-1：大文件输入卡顿，根因是 `stripTypes` 的 `<` 扫描

#### 现象

在独立页面中对合成 TS 文件模拟一次按键，走真实的 `onSourceChanged → updateEditorChrome` 路径：

| 文件规模 | 单次按键处理耗时 |
|---|---|
| 21 行（lcs 样例） | 7.3 ms |
| 36 行（showcase 样例） | 13.3 ms |
| 37 行（mergesort 样例） | 12.9 ms |
| 178 行 | 30.1 ms |
| 353 行 | 63.9 ms |
| 703 行 | 166.9 ms |
| 1403 行 | 555.4 ms |

对同样的 703/1403 行函数文件，`stripTypes(src)` 单独耗时约 85/360 ms；`collectNames` 只有 4/8 ms，`blankStrings` 只有 0.5/5.2 ms。也就是说，主要成本在 `stripTypes`，不是名字收集本身。

#### 根因

调用链：

1. 编辑器输入触发 `onSourceChanged`（`index.html:8781`）。
2. 它调用 `updateEditorChrome`（`index.html:6094`）。
3. `updateEditorChrome` 调用 `collectDeclaredNames`（`index.html:6097`）。
4. `collectDeclaredNames` 对每个新文本调用一次 `stripTypes`（`index.html:5745`）。

`stripTypes` 在读取一个标识符后，会向前跳过空白，如果遇到 `<`，会尝试把它当成泛型参数并寻找配对的 `>`（`index.html:1837-1863`）。这段扫描只以“找到配对的 `>`”或“到达文件末尾”结束，**没有在换行处停止**。

因此，一段普通比较表达式：

```ts
for (let j = 0; j < nums.length; j++) { ... }
```

如果它后面没有同一文件内可配对的 `>`，每个 `<` 都会从当前位置一直扫描到文件末尾。文件中 `<` 越多、文件越长，总成本越接近 O(n²)。

#### 对照实验

| 1400 行 / 约 25 KB 的合成文件 | `stripTypes` 耗时 |
|---|---|
| 每行 `let xN = a + b;` | 7.4 ms |
| 每行 `let xN = a < b;` | **1962.7 ms** |
| 700 行函数，循环条件用 `<` | 约 85 ms |
| 1400 行函数，循环条件用 `<` | 约 360 ms |
| 同样 1400 行函数，把 `<` 换成 `!==` | 约 7 ms |
| 同样 1400 行函数，把 `<` 换成 `>` | 约 7 ms |
| 1400 行普通赋值 | 3.5 ms |

这组对照基本可以确认：触发点是 `<`，且扫描没有行边界保护。`tryStripGenericArrow`（`index.html:1437-1470`）本身会在换行处返回，真正的问题在标识符后面的第二段泛型扫描。

#### 次要成本

在同一批 703/1403 行文件上：

- `typecheckTS` 约 36–60 ms（不同样本波动较大，178–1403 行范围内曾测得 18–71 ms）。
- CodeMirror 名字装饰重建约 10–35 ms（`editor/cm-entry.js:428-450`）。
- 每次文本变化都会重建“已声明名字”和“内置名字”两套装饰，且 `nonCodeRanges` 会扫描全文（`editor/cm-entry.js:187-224`）。

这些是次级问题；先修复 `stripTypes` 的二次扫描，输入延迟会下降一个数量级。

#### 影响判断

- 20–40 行：7–13 ms，正常。
- 100–300 行：可能开始有轻微延迟，取决于 `<` 出现次数。
- 700 行以上：明显卡顿；文件越大越接近平方级增长。
- 本次 1400 行文件是压力样本，但它暴露的是确定性代码路径，不是测量噪声。

#### 建议

1. 在标识符后的泛型扫描中增加换行边界：遇到 `\n` 立即放弃，不跨行寻找 `>`。
2. 只在前方是标识符/调用、且同一行能配平 `<>`、后面紧跟 `(` 时才按泛型处理。
3. 为“大量 `<`、没有 `>`”的文件增加回归测试。
4. 实时类型诊断可加 100–150 ms debounce；不要阻塞每次按键的编辑体验。
5. 可选：把 `stripTypes` 结果按源码文本缓存，避免一次输入内重复解析。

粗略工作量：0.5–1 天（含回归测试）。

验收参考：1000 行压力文件单次按键 < 30 ms；`stripTypes` 本身 < 20 ms。

### P1-2：TS 长轨迹的整段同步重放

#### 现象

- 602 步冒泡排序：按需计算全部步骤共 100.8 ms。
- 1403 步循环：按需计算全部步骤共 931.5 ms。
- 2403 步执行“运行到下一个检查点”（无检查点，实际运行到结束）：**1917 ms**。
- 3003 步同样操作：**2562 ms**。
- 3000 步轨迹上普通步进 100 次：平均 15.0 ms，p95 24.3 ms，最大 38.6 ms。
- 1400 步轨迹上步进 300 次：平均约 10.6–12.9 ms，p95 19.5 ms，最大 35.7 ms。

手动步进还能接受；问题在于“运行到结束”或“运行到下一个检查点”会同步计算全部剩余步骤。

#### 根因

`computeAndAppendNextStep`（`index.html:5268`）每次新增一步时，都会重新执行编译后的整个函数，从程序开头跑到目标步，再通过 `PAUSE_SIGNAL` 停下：

- 目标步之前的插桩钩子全部执行，只是不记录快照。
- 目标步才采集 `v`、`ds` 和调用栈。
- 因此第 S 步的成本与 S 成正比，生成完整轨迹的总成本是 O(S²)。

`runToNextCheckpoint`（`index.html:7049-7066`）又在一个同步 `while` 循环里连续调用它，直到检查点、错误或结束；期间不让出主线程。`MAX_EXEC_MS = 3500` 只限制单步重放时长，不能限制整个循环的总时长；`MAX_STEPS = 5000` 则允许一次同步循环跑到 5000 步。

按实测趋势外推，5000 步的“运行到结束”可能在 5–8 秒量级（估算值，未直接跑满 5000 步）。

#### 建议

1. 将 `runToNextCheckpoint` 改为分片执行：每 12–16 ms 或每 N 步检查一次截止时间，然后 `setTimeout`/`requestAnimationFrame` 继续，主线程可响应点击和滚动。
2. 增加“正在计算第 x/y 步”的进度与取消入口。
3. 长期方案：使用可暂停的解释器/快照，或每隔一定步数缓存执行状态，避免每步从头重放。
4. 渲染也应按需更新；但第一优先是解除同步长循环。

粗略工作量：分片与进度 1–2 天；快照式执行引擎另计。

验收参考：运行到结束过程中不出现 >100 ms 的长任务；用户可随时取消。

### P1/P2：Python 大结构快照与主线程构建

#### 现象

| 场景 | 步数 | Worker 执行 | 主线程构建 | 单步渲染 | 观测堆 |
|---|---:|---:|---:|---:|---:|
| 简单循环 | 1203 | 214 ms | 74 ms | — | 约 19 MB |
| 12×12 DP | 328 | 725 ms | 74 ms | 14.8 ms | 约 10 MB |
| 18×18 DP | 706 | **3567 ms** | 294 ms | 22.6 ms | 约 24 MB |
| 25×25 DP | — | 超过 15 秒仍未完成，采集超时 | 未拆分 | — | 超时后约 42 MB |

25×25 的结果受采集器 15 秒超时限制，无法确认 Worker 与主线程各占多少；上表其它行是完整返回后的分段测量。

#### 根因

1. **普通“运行”仍然完整 trace**  
   `runOnly`（`python/py_engine.js:776-797`）调用 `run(src, { maxSteps: 2000, timeLimit: 6 })`。Worker 仍执行 `run_trace_json`，逐行安装 `sys.settrace`、采集变量和栈、序列化全部步骤；`runOnly` 最后只使用 `stdout`、错误和返回值，步骤被丢弃。运行路径为此支付了完整的调试记录成本。

2. **栈顶帧变量被重复序列化**  
   `_Recorder.trace` 先采集当前帧 locals 并序列化（`python/py_bridge.py:394-398`），随后 `_stack_snapshot` 又遍历调用栈，并对每一帧（包括栈顶）再次采集和序列化 locals（`python/py_bridge.py:359-381`）。栈顶帧在每步都被处理两次。

3. **全部步骤一次性返回**  
   `run_trace_json` 把所有 steps 一次性 `json.dumps` 返回（`python/py_bridge.py:703-714`），Worker 到主线程的 JSON 体积随“步数 × 快照大小”增长。

4. **主线程一次性构建所有步骤**  
   `buildSteps`（`python/py_engine.js:607-643`）对每个 step 做 hydrate、clone、classify、populateInterfaceSchemas、构建调用栈和动画。700 步时 294 ms，长轨迹或大结构会线性放大；Python 的 2000 步上限下仍可能产生数百 MB 级中间对象。

5. **重复编译**  
   `check_syntax_json` 会 `compile` 一次（`python/py_bridge.py:432-435`），随后 `run_trace_json` 又 `ast.parse` + `compile`（`python/py_bridge.py:622-624`）。这是次要成本，但可以在一次请求内复用。

#### 建议

1. 为“运行”增加不 trace 的执行路径：直接 `exec`，只捕获 stdout、异常和入口返回值；不调用 `sys.settrace`。
2. 复用语法检查阶段的编译结果，或把检查与运行合并成一次请求。
3. 栈快照接收已采集的栈顶 locals，避免重复 `_capture_locals` / `_tag_value`。
4. 快照只记录变化字段，或按步数/总字节预算截断；当前虽有深度、条目数和节点预算，但没有按总 payload 大小限制。
5. 主线程按需构建步骤或分片构建，不要一次处理整包；必要时把轻量 hydrate 也移到 Worker。
6. Worker 请求超时应真正终止当前 Worker，避免超时后旧任务继续占用资源。

粗略工作量：无 trace 运行 + 去重 + 复用编译 1–2 天；分片/按需构建另需 1–2 天。

验收参考：30×30 DP 调试轨迹在 3 秒内完成；同样代码的普通“运行”不产生完整 trace；主线程不出现秒级阻塞。

### P3：每步全量渲染与资源加载

#### 现象

- 每步 `renderStatic`（`index.html:6914`）重建调用栈、原始变量、控制台描述和整个槽位区。
- `renderPicker`（`index.html:6859`）和 `renderSlots` 都调用 `discoverVars`（`index.html:6848`），后者每次扫描全部历史步骤。
- 3000 步轨迹上步进平均 15 ms、p95 24 ms；1403 步时 `renderStatic` 单次约 9 ms。
- 首屏资源：`index.html` 348 KB、CodeMirror bundle 553 KB、`python/py_engine.js` 39 KB、`app-session.js` 12 KB；本地 DOMContentLoaded 约 428 ms。
- `python/serve.mjs:32-35` 使用 `Cache-Control: no-store`，本地刷新会重新请求全部静态资源。

#### 建议

1. 变量列表缓存：只在步骤增加时增量更新，不每帧扫描全部历史步骤。
2. 面板做差量更新；未变化的调用栈、槽位和静态变量不重建。
3. 对隐藏/不可见槽位延迟渲染。
4. 部署时给带内容 hash 的 `editor/cm.bundle.js` 设置长期缓存；`index.html` 保持协商缓存。
5. CodeMirror 名字装饰的区间重叠检查可改为排序后二分/双指针；当前是次级成本。

## 表现良好的部分

- TS 调试是按下需要步计算的，`startDebug` 不会预先跑完整个程序；短轨迹启动很快。
- 快照有明确的展示上限：数组 40、网格 30×30、树 31 节点、链表 30、Map/Set 40，避免渲染无限膨胀。
- Python 执行放在 Worker 中，Python 本身不阻塞主线程；问题主要集中在记录、序列化和主线程后处理。
- CodeMirror 的词匹配只扫描可见区域，并限制 200 个装饰；检查点 gutter 只处理可见行。
- 自动保存有 500 ms debounce（`app-session.js:62-66`）。
- 现有 `test-pipeline.mjs` 在基线上全部通过，可作为修复后的回归基线。

## 建议实施顺序

1. **先修 `stripTypes` 的 `<` 行边界 + 回归测试**（0.5–1 天）。这是投入最小、收益最直接的一项。
2. **给实时诊断加 debounce**（0.5 天），避免每次按键都做完整类型检查。
3. **分片 `runToNextCheckpoint`**（1–2 天），解决秒级主线程冻结。
4. **Python 无 trace 运行 + 栈顶帧去重 + 编译复用**（1–2 天），先把普通运行和中等结构的速度拉回来。
5. **Python 按需/分片构建步骤**（1–2 天），再处理超大网格。
6. **渲染增量更新与部署缓存**（3–5 天，可后置），主要面向长轨迹和 60fps 视频导出。

## 复现方法

### 基础命令

```bash
node test-pipeline.mjs
HOST=127.0.0.1 PORT=5187 node python/serve.mjs
```

打开 `http://127.0.0.1:5187/`，在浏览器控制台或页面自动化中调用应用已有函数。

### 合成输入样本

大文件按键场景：

```ts
function task0(nums: number[]): number {
  let total: number = 0;
  for (let j = 0; j < nums.length; j++) {
    total = total + nums[j];
  }
  return total;
}
```

将 `task0` 复制成不同的函数名，生成 100–200 份。

`<` 单独对照：

```ts
let x0 = a < b;
let x1 = a < b;
// ...
```

执行：

```js
stripTypes(src);
```

### 长轨迹场景

```ts
let sum: number = 0;
for (let i = 0; i < 1500; i++) {
  sum = sum + i;
}
sum;
```

调用 `runToNextCheckpoint()`，测量同步耗时和 `TRACE.steps.length`。

### Python 大结构场景

```python
n = 18
dp = [[0] * n for _ in range(n)]
for i in range(n):
    for j in range(n):
        dp[i][j] = i + j
print(dp[n - 1][n - 1])
```

分别测量 `PY_ENGINE.run(src, { maxSteps: 2000, timeLimit: 8 })`、`PY_ENGINE.buildSteps(payload, lines)` 和 `renderStatic`。

## 测量限制

- 所有数据来自单机、单浏览器、无 CPU 降频环境，不能直接代表低端设备。
- 1400 行合成文件是压力样本；真实算法代码通常更短，但大文件导入、粘贴和长函数仍会触发同一路径。
- Pyodide 使用浏览器缓存，冷启动、CDN 抖动和离线失败未纳入本次数据。
- 25×25 Python 用例只确认“超过 15 秒未返回”，未完成精确分段。
- 内存数字受 GC 影响，只能说明量级；本报告不构成内存泄漏结论。
- 未测试视频导出逐帧性能；该项目已知仍是半成品。
- 未在真实静态部署环境验证缓存策略与首屏时间。
